# 関連 OSS 2 件を、自作サンプルで動かした記録（2026-11）

> 12 か月・同じ採点での比較評価は `results/oss-evaluation-2026-11.md`。ここは動作確認と不具合の記録。

実行場所：Claude Code クラウド（x86_64）、2026-11-21。どちらのプロジェクトにも、まだ何も投稿していない。

## 使ったサンプル
`samples/` の自作サンプル（架空の月次明細、A4 1 ページ × 3 か月、同じ書式）を 2 種類。
- **図形版**：文字をすべて塗りつぶしの輪郭で描いた。フォント無し、`pdftotext` は何も返さない。
- **フォント版**：同じページを、文字コードの手がかりを全部抜いた埋め込みフォントで描いた
  （ToUnicode なし・cmap 表なし・字形名なし・コードは初出順の連番）。
  表示は正常、`pdftotext` は `!"#$%&'` のような記号の羅列になる。
- 似た字（0/O、1/l/I）を品番に混ぜた。2 月に `%`、3 月に `#` と `Q`（数回しか出ない字、その月だけの字）を入れた。

## 1. pdf-glyph-mapping
- https://github.com/shreevatsa/pdf-glyph-mapping （MIT）。試したのは `7b4075b`（2025-06-17）。
- README いわく「ほぼ放置」。作者自身の issue #10「Get this working again」（2024-02 作成）が開いたまま。

**中身**：PDF からフォントと文字列（字形番号の並び）を取り出し、字形を画像で並べた HTML を作る。
人が TOML に「この字形番号はこの文字」と書き（README いわく "main manual grunt work"）、
それを使って `/ActualText` 付きの PDF を作り直す。主な対象はデーヴァナーガリー文字。

**動かした結果**（rustc 1.97.0、mutool 1.23.10。Makefile は使わず 1 段ずつ。**無修正の `7b4075b`** で確認し、そのうえで直し方を試した）

入力は 3 種類：
(a) フォント版 3 月分そのまま（中身は非圧縮）、
(b) (a) を pikepdf で保存し直したもの（中身が Flate 圧縮。普通の PDF はこちら）、
(c) (b) に、57 字形のうち奇数番の 29 個だけの ToUnicode を足したもの（文字情報が一部だけある PDF）。

| 段 | 結果 |
| --- | --- |
| `cargo build --release` | 通る（警告のみ） |
| `mutool extract` → `glyph-dumper` | 動く。字形 57 個を PNG に出力 |
| `dump-tjs --phase phase1` | 動く。ToUnicode があれば `font-…-cmap.toml` も書く（(c) で 29 件） |
| ① `src/sample-runs.py` | **(a)(c) とも `FileNotFoundError`**。`font-….toml` を探すが、phase 1 が書くのは `font-…-cmap.toml`（しかも ToUnicode が無ければ何も書かない） |
| ② 〃（空の `.toml` を置いて先へ進めた場合） | **`AssertionError`**。`.Tjs` の中身が `CharacterCode([0, 1])` という Rust のデバッグ表記で、4 桁 16 進（`0001`）を期待する側と合わない |
| 人が TOML を書く → `src/validate_maps.py` | 動く |
| ③ `dump-tjs --phase phase2` | **検証済みの対応表を読まない**。phase 2 が読むのは `*<フォント名>-cmap.toml`（phase 1 と同じ `mapped = [[[0, 1], ["M"]], …]` 形式）だけで、`validate_maps.py` が書く `[0001] replacement_text = "M"` 形式は読まれない。全字形が `[glyph[0, 1]]` という代替文字になる |
| ④ 〃（入力の中身が圧縮されているとき：(b)(c)） | **壊れた PDF を書き出す**。`pdftotext` は `Unknown compression method in flate stream`。(a) では起きない |
| Makefile | `cargo +nightly` と作者の手元のパス（`ORIG=../../gp-mbh/unabridged`）が固定 |

原因と直し方（手元で確認、`pdf-glyph-mapping-fixes.patch`）：
- ② `text_state.rs`：`format!("{:?} ", n)`（変数名は `glyph_hexes`）を、バイトの 16 進表記に変える 1 か所。直すと HTML と TOML の下書きまで出る。
- ④ `pdf_visit.rs`：書き換えた中身を `set_content` で戻しているため、元の `/Filter /FlateDecode` が残ったまま非圧縮のデータが入る。
  lopdf 0.26 にある `set_plain_content`（`/Filter` と `/DecodeParms` を外す）に変える 1 か所。直すと (b)(c) とも読める PDF になり、`mutool info` もエラー 0。
- ①③ は「Python 側と Rust 側のどちらの名前・形式に合わせるか」の判断が要るので、手は入れていない。
- **phase 2 そのものは正しく動く**：②④を直した版に、phase 1 と同じ形式で 57 字形すべての正しい対応を渡すと、(b) から 82 行すべてが正解と完全に一致する `/ActualText` が付いた。
- 2025-06 に Rust 側をワークスペースに作り直したとき、Python 側と Makefile が追いついていないとみられる。作者の issue #10「Get this working again」の中身そのもの。
- 既存の issue・PR（#1〜#10）に、①〜④と同じ報告は無い（2026-11-21 確認）。
- 確認済み（下の「作者自身の作業例で確かめた」）：デーヴァナーガリー（1 字形が複数文字になる）でも修正版は作者の出力と一致。issue #5 は 12,000 ページの自作 PDF では再現せず。

**作者自身の作業例で確かめた（2026-11-22）**
作者のリポジトリの `work/example/unabridged-page-201.pdf`（デーヴァナーガリーの本の 1 ページ）と、作者が書いた対応表 `work/maps/valid/*.toml` を使った。
- phase 1（無修正版）：`.Tjs` は `CharacterCode([...])` 表記、`font-…-cmap.toml` を書く → `sample-runs.py` は `font-….toml` を探して **`FileNotFoundError`**（①、作者のデータでも起きる）。
  名前を合わせると、Rust が書いた `-cmap.toml`（入れ子の配列）を Python の `toml` 0.10.2（Debian `python3-toml`）が読めず **`IndexError`**。名前だけでなく中身の形式も食い違っている。
- phase 2：作者の対応表（`[0005] replacement_text = …` 形式）を、phase 2 が読む `mapped = [[[0, 5], ["ँ"]], …]` 形式に変換して渡した。
  - **無修正版：壊れた PDF**（`Unknown compression method in flate stream`）。④が作者のデータでも起きる。
  - **修正版（`pdf-glyph-mapping-fixes.patch`）**：全字形に対応が見つかり、`/ActualText` 284 個のうち **278 個が、作者がリポジトリに置いている修正済み PDF（`unabridged.fixed-page-201.pdf`）と完全に一致**。
    残り 6 個：1 個は私の比較スクリプトがフォント名の目印を外し損ねただけ（中身は同じ）。5 個は字形 `01C2` を含む文字列で、このページで `01C2` はちょうど 5 回出る。今の対応表では `01C2` → 「ों」、作者の古い出力では「र्<CCprec>े」。**対応表が後から直されたための違い**で、修正 2 か所（`.Tjs` の書式、圧縮の印）は対応表の引き方に触れていない。
- issue #5（大きな PDF での異常終了）：自作のフォント版 1 ページを 12,000 ページに複製した PDF で、無修正版・修正版とも 3 回ずつ phase 1 を実行。**異常終了は起きなかった**（このサンプルでは再現せず。作者の PDF とは別物）。
  ついでに分かったこと：全ページが**同じ圧縮済みの中身を共有する** PDF では、無修正版は最初の 1 ページ分（82 行）しか出さなかった（④で共有の中身が書き換わるため）。ページごとに中身が別なら無修正版も全ページ（984,000 行）を出す。修正版はどちらも全ページ。

**学んだこと**
- 対応表づくりは全部手作業。生成 AI に下書きさせて人が確かめる形にすると、ここが一番楽になる。
- 字形を「番号」で見分ける前提なので、文字が図形だけの PDF には使えない。形でまとめる段階が別に要る。

## 2. CUNY AI Lab pdf-accessibility-app
- https://github.com/CUNY-AI-Lab/pdf-accessibility-app （AGPL-3.0）。試したのは `8213721`（2026-11-19）。活発に更新中。
- PDF をアクセシブル（PDF/UA）に直すアプリ。その一部 `backend/app/pipeline/fonts/ocr_unicode.py`（PR #82）が近い。

**中身**：文字情報の無いフォントの字形を、ページ画像を Tesseract で読ませて**投票**で決める。
- 2 回以上・6 割以上が一致し、2 位の 3 倍以上なら確定（`MIN_AGREEMENT = 0.6`、`LEAD_RATIO = 3`）。
- 1 回しか出ない字は、OCR の自信度 90 以上でないと確定しない（`MIN_SINGLE_CONFIDENCE = 90.0`）。
- 同じ輪郭の字形は、輪郭のハッシュ（完全一致）でまとめて一緒に投票する。
- 2 つの形が同じ文字に読まれたら、票の多い方だけ残す。決まらない字は未確定のまま。

**動かし方**：アプリ全体ではなく `_recover_sync` だけを呼んだ（`tools/run_cuny_ocr_unicode.py`）。
依存はロックファイルと同じ版（pikepdf 10.17.0、pypdfium2 5.6.0、pdfminer.six 20260107、fonttools 4.62.1、
pydantic 2.12.5、pydantic-settings 2.13.1、Python 3.12）＋ Tesseract 5.3.4。
設定の検証が LLM の API キーを求めるので `LLM_BASE_URL=http://localhost:1/v1` を指定した（この処理は LLM を呼ばない）。
直した PDF を `tools/compare_rows.py` で正解と 1 字ずつ比べた（空白は除く）。

| サンプル | 対象字形 | 確定 | 正しい文字 | **誤り** | 未確定の文字 |
| --- | --- | --- | --- | --- | --- |
| フォント版 1 月 | 54 | 51 | 418 | **0** | 29（l 16、I 8、O 5） |
| フォント版 2 月 | 55 | 53 | 454 | **0** | 16（I 10、O 6） |
| フォント版 3 月 | 57 | 55 | 476 | **0** | 13（O 7、I 6） |
| 図形版 | — | — | — | — | この処理の対象外（下の「図形版の扱い」） |

同じサンプルを作り直して 2 回実行し、同じ数字になった。
環境の確かめ：プロジェクト自身のテスト `tests/test_ocr_unicode.py` が、この環境で 5 件すべて通った
（本物の Tesseract を使うものを含む。テストのために sqlalchemy 2.0.49、rapidfuzz 3.14.3、docling-parse（版は未固定）を追加）。

**図形版の扱い（アプリの別の段階）**
最初「図形版は対象外」と書いたのは、上の処理（`ocr_unicode`）だけの話だった。アプリ全体では、
分類の段階（`app/pipeline/classify.py` の `_vector_outline_pages`）が「文字が無く、図形が 100 個以上・線分が 1000 本以上のページ」を
文字が図形で描かれたページとして見つけ、そのページだけ OCRmyPDF の `--force-ocr` で読み直す。
- この判定を図形版にかけると、ページ 0 が見つかった（フォント版は見つからない）。
- `build_ocrmypdf_args` が作る引数（`--rotate-pages --deskew --force-ocr --pages 1 --optimize 0`、言語 eng）のまま、
  OCRmyPDF 17.4.0（Ghostscript 10.02.1、Tesseract 5.3.4）で 3 か月分を読み、`tools/compare_text.py` で正解と比べた（空白は除く）。
  アプリ全体の流れ（キューやその後の段階）は通していない。

| 図形版 | 正しい文字 | **別の字に置き換わった** | 抜けた | 余分 |
| --- | --- | --- | --- | --- |
| 1 月 | 436 | **9** | 2 | 1 |
| 2 月 | 459 | **11** | 0 | 1 |
| 3 月 | 472 | **15** | 2 | 1 |

- 置き換わりは似た字（O↔0、l→1、I→1、I↔l）がほとんど。品番 14 行のうち 1 月 9 行・2 月 11 行・3 月 14 行が違う品番になった。
- **金額も 1 か所変わった**：1 月の `5,583` が `5,983`。どこにも印は付かない。
- 余分の 1 字は、`Il-628` が `IIl-628` になったような、無い字が足されたもの。
- 同じ入力でもう一度読むと、3 か月とも同じ結果（ぶれは無い）。
- フォント版の処理（投票）が「決めきれない字は未確定のまま残す」のに対し、ページ全体の OCR は**黙って別の字にする**。
- サンプルの性質：Liberation Sans では I と l がほぼ同じ形（高さが約 5% 違うだけ）。人の目でも見分けにくい、厳しめの試験になっている。

**学んだこと**
- **でっち上げはゼロ**。3 月だけの `#`・`Q` も正しく確定した。
- 未確定は**すべて似た字**。Tesseract は O を 0 と読みがち（3 月：0 が 6 票、O が 1 票）で、
  本物の 0 の方が票が多いので O が外れる。I と 1 は 3 票ずつで決まらない。
- **文書ごとに独立**：1 月は l を決められず、2・3 月は決められた。確定した対応を次の文書へ持ち越さない。
  一度人が確かめた対応表を毎回使う方式なら、未確定は回を追うごとに減るはず（未測定）。
- 文字が図形の PDF は、ページ全体の OCR に回る。そこでは似た字が黙って置き換わり、金額の数字も 1 か所変わった。
  帳簿方式なら、形の違い（I と l の高さの差など）を人が一度確かめれば、以後は毎回同じ答えになるはず（未測定）。
- 形のまとめ方が完全一致のハッシュ。フォント内の字形なら足りるが、図形だけの PDF では
  座標の丸めで形が少しずつずれるので、「似ている度合い」でまとめる必要がある。
